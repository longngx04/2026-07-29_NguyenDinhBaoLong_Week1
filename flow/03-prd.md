## Context

Project Sentinel needs trustworthy raw SAST evidence before it can normalize data, build a knowledge base, or ask an AI agent to analyze security findings. The target is OWASP WebGoat, an intentionally insecure Java/Spring training application, and it is run only in the local Docker test environment. The Week-1 delivery is a small CLI-oriented repository that pins the target source/runtime and invokes OpenGrep plus FindSecBugs with stored raw artifacts. This avoids interpreting, remediating, or actively exploiting findings at this stage.

## Target users

Primary user: a VinUni × VinSOC Project Sentinel intern who clones the repository, starts the authorized local target, and needs to generate scanner output for review. Reviewer: mentor Dương Mạnh Kiên, who needs to inspect the two tools' raw output and confirm a baseline exists. Both users work from the project README and GitHub Actions artifacts, not a hosted product UI.

## Problem statement

Without a pinned target and two reproducible SAST outputs, the project cannot supply defensible input to the Week-2 normalization and evaluation work. The Week-1 solution must make the raw evidence reproducible for a new team member without exposing the intentionally vulnerable target to the network.

## Features (user-centric — action → observable result)

Tag each v1 feature with a stable id `FRn:` (functional requirement) — the traceability
anchor. Every `FRn` must later be claimed by a card (`implements: FRn`) and served by an
interface in the contract (`FRn →`); `/flow consistency` checks this mechanically.

- FR1: As an intern, I run the local target command and see WebGoat `v2025.3` available only at `http://127.0.0.1:8080/WebGoat/` after its health check succeeds.
- FR2: As an intern, I run the OpenGrep scan command and receive a valid JSON report at `results/raw/opengrep.json`, generated with the checked-in Java rule pack and documented scanner version.
- FR3: As an intern, I run the baseline scan command and receive a valid SARIF report at `results/raw/findsecbugs.sarif`, generated by FindSecBugs against the compiled pinned WebGoat source.
- FR4: As a reviewer, I trigger or inspect the GitHub Actions workflow and can download the two raw reports from its artifacts after the same scans complete.
- FR5: As an intern or reviewer, I follow the README and can identify the components, safe start/stop commands, scan commands, output paths, principal WebGoat endpoints, and explicitly stated Week-1 limits.

## Non-functional requirements

- The WebGoat container must bind its exposed ports to `127.0.0.1` only; no public deployment, active exploitation, or gateway is part of Week 1.
- Source tag, image tag, tool versions, and OpenGrep rules must be committed/pinned; scan results must state their tool metadata where supported.
- Scan commands must treat findings as data (not a process error) while still failing on setup, build, scanner, or malformed-output errors.
- Scanners must not edit the WebGoat submodule; output is limited to `results/raw/` and CI artifacts.

## Tech stack

Docker Compose runs `webgoat/webgoat:v2025.3` on the local host. A Git submodule pins `WebGoat/WebGoat` source to `v2025.3`; a dedicated scanner image combines Eclipse Temurin JDK 23, the Maven wrapper from WebGoat, OpenGrep `v1.26.0`, and FindSecBugs `1.14.0`. Bash/Make provide local commands, GitHub Actions runs the same scan entrypoint, and raw JSON/SARIF files are retained as artifacts. There is no application backend, database, frontend, hosted deploy, or LLM in Week 1.

## Success metric (numbers only)

For one clean checkout, 2 out of 2 scanners complete without operational errors, `results/raw/opengrep.json` parses as JSON, `results/raw/findsecbugs.sarif` parses as JSON/SARIF, and 1 out of 1 GitHub Actions run uploads both files as an artifact; WebGoat health check returns HTTP 200 before the recorded demo.
